# Greenlight API

A JSON API for retrieving and managing information about movies. Written in Go with PostgreSQL as the datastore.

The API supports full CRUD on movie records, stateful token authentication, permission based authorization, activation emails, rate limiting, CORS, structured logging, runtime metrics and graceful shutdown.

## Stack

| Component | Choice |
|---|---|
| Language | Go 1.25 |
| Database | PostgreSQL (with `citext` extension) |
| Router | `julienschmidt/httprouter` |
| DB driver | `lib/pq` |
| Mail | `wneessen/go-mail` |
| Rate limiting | `golang.org/x/time/rate` |
| Password hashing | `golang.org/x/crypto/bcrypt` |
| Linting | `staticcheck` (declared as a Go tool dependency) |

No web framework and no ORM. The standard library does the heavy lifting; the third party packages cover only what the standard library does not.

## Architecture

The project follows the standard Go layout of a thin `cmd` layer over reusable `internal` packages.

```
cmd/api/            HTTP layer: handlers, middleware, routing, server lifecycle
cmd/examples/cors/  Small static pages used to manually exercise CORS behaviour
internal/data/      Domain models and all SQL. The persistence boundary.
internal/mailer/    SMTP client with embedded HTML/text templates
internal/validator/ Reusable validation primitives
internal/vcs/       Build time version string, read from the embedded build info
migrations/         Sequential up/down SQL migrations, applied manually
```

### Dependency direction

```
cmd/api  ->  internal/data  ->  database/sql  ->  PostgreSQL
   |
   +------>  internal/mailer  ->  SMTP
   +------>  internal/validator
```

`internal/data` never imports anything from `cmd`. Handlers never write SQL. The two layers meet at the `data.Models` struct, which is a single container holding one model per table (`Movies`, `Users`, `Tokens`, `Permissions`) and is constructed once in `main()` and injected into the application struct.

### Application struct as the dependency container

There is no global state and no service locator. A single `application` struct holds the config, the logger, the models, the mailer and a `sync.WaitGroup`. Every handler and middleware is a method on `*application`, so dependencies are available without package level variables and the whole thing stays trivially testable.

### Request pipeline

Every request passes through the middleware chain built in `cmd/api/routes.go`, outermost first:

```
metrics -> recoverPanic -> enableCORS -> rateLimit -> authenticate -> router -> handler
```

The ordering is deliberate:

- `metrics` sits outermost so timing and status codes cover the entire chain, including responses generated by the middleware below it.
- `recoverPanic` converts a panic in any downstream handler into a `500` response with `Connection: close`, instead of taking the process down.
- `enableCORS` runs before rate limiting so preflight `OPTIONS` requests are answered even when the client is near its limit.
- `rateLimit` is per client IP, using a token bucket per IP held in a map guarded by a mutex. A background goroutine sweeps entries that have not been seen for three minutes so the map cannot grow without bound.
- `authenticate` resolves the bearer token to a user and stores it in the request context. A missing `Authorization` header yields the anonymous user rather than an error, which keeps the public endpoints on the same code path.

Authorization is layered on top of authentication as composable handler wrappers, applied per route:

```
requirePermission(code) -> requireActivatedUser -> requireAuthenticatedUser -> handler
```

Each stage only checks its own condition and delegates the rest, so a route asks for the strongest guarantee it needs and the weaker checks come along automatically.

### Authentication and tokens

Authentication is stateful bearer token, not JWT. On login the API issues a 26 byte random plaintext token with a 24 hour lifetime and stores only its SHA-256 hash in the `tokens` table. The plaintext is returned to the client once and never persisted, so a database leak does not hand over usable credentials. Activation tokens use the same mechanism under a different scope with a three day lifetime.

Passwords are hashed with bcrypt at cost 12. The `password` type keeps its hash unexported and exposes only `Set` and `Matches`, so no handler can accidentally touch the raw bytes, and the `User` struct is tagged so credentials can never be serialized into a response.

Permissions are stored relationally as `permissions` and a `users_permissions` join table, seeded with `movies:read` and `movies:write`. Adding a new capability is a migration, not a code change.

### Concurrency and background work

Slow, non essential work such as sending the welcome email is dispatched through an `app.background()` helper. It runs the function in a goroutine tracked by the application `WaitGroup` and wraps it in its own `recover()`, so a failing email cannot slow down the response or crash the server. On `SIGINT` or `SIGTERM` the server stops accepting connections, gives in flight requests up to 30 seconds to finish, then waits on the `WaitGroup` before exiting, so queued background jobs are not lost mid shutdown.

### Data access decisions

- Every query runs with a three second `context` timeout, so a stalled database cannot pin server goroutines indefinitely.
- Updates use optimistic concurrency. Each row carries a `version` column, `UPDATE` statements include the expected version in the `WHERE` clause, and a zero row result surfaces as `ErrEditConflict` and a `409` response. This avoids row locks while still preventing lost updates on concurrent `PATCH` requests.
- Partial updates are modelled with pointer fields in the input struct, so an absent JSON key and an explicit `null` are distinguishable.
- Listing uses a single query for both the page and the total count, via `count(*) OVER()`, rather than a separate count round trip.
- Full text search uses a GIN index over `to_tsvector('simple', title)`, and genre filtering uses a GIN index on the `genres` array with the `@>` containment operator.
- Sort columns are never interpolated from raw user input. The requested value is validated against a per endpoint safe list before it reaches the query string, and `sortColumn()` panics if that check was somehow bypassed.

### JSON handling

Responses are enveloped (`{"movie": {...}}`) so the shape stays stable when metadata is added and the response can never be a top level array. Request decoding is strict: the body is capped at 1MB, unknown fields are rejected, a second `Decode` call catches trailing content, and the decoder's error types are translated into readable client messages rather than leaking Go internals. The `Runtime` type implements `MarshalJSON` and `UnmarshalJSON` so runtimes travel over the wire as `"107 mins"` while staying an `int` in the domain model.

### Observability

Structured logs go to stdout via `log/slog`, which keeps the application free of any assumption about log destinations and leaves collection to the runtime environment. Runtime metrics are exposed at `/debug/vars` through `expvar`: build version, goroutine count, database connection pool stats, request and response counts, response counts by status code, and cumulative processing time.

## API

Base path is `/v1`.

| Method | Endpoint | Permission | Description |
|---|---|---|---|
| GET | `/v1/healthcheck` | public | Status, environment and version |
| POST | `/v1/users` | public | Register a user and send an activation email |
| PUT | `/v1/users/activated` | public | Activate a user with an activation token |
| POST | `/v1/tokens/authentication` | public | Exchange credentials for a bearer token |
| GET | `/v1/movies` | `movies:read` | List movies with filters, sort and pagination |
| POST | `/v1/movies` | `movies:write` | Create a movie |
| GET | `/v1/movies/:id` | `movies:read` | Fetch a single movie |
| PATCH | `/v1/movies/:id` | `movies:write` | Partially update a movie |
| DELETE | `/v1/movies/:id` | `movies:write` | Delete a movie |
| GET | `/debug/vars` | public | `expvar` metrics |

Authenticated requests carry the token as `Authorization: Bearer <token>`.

`GET /v1/movies` accepts `title`, `genres` (comma separated), `page`, `page_size` and `sort`. Sort accepts `id`, `title`, `year` and `runtime`, each optionally prefixed with `-` for descending order. The response includes a `metadata` object with the current page, page size, first and last page, and total record count.

### Example

```shell
curl -X POST http://localhost:4000/v1/tokens/authentication \
  -d '{"email":"alice@example.com","password":"pa55word"}'

curl -H "Authorization: Bearer <token>" \
  "http://localhost:4000/v1/movies?genres=drama&sort=-year&page_size=10"
```

Errors are always JSON, in the form `{"error": ...}`. Validation failures return a `422` with a field keyed map of messages.

## Getting started

### Prerequisites

- Go 1.25 or later
- PostgreSQL 15 or later. Development runs it as a Docker container rather than a native install, so the same version can be torn down and recreated without touching the host
- [Mailpit](https://github.com/axllent/mailpit) or any SMTP server. Development defaults point at Mailpit on `127.0.0.1:1025`, which captures outbound mail locally instead of relying on a third party mail testing service

### Database setup

Connect to the running PostgreSQL container:

```shell
docker exec -it <postgres-container> psql -U <superuser> -d <default-db>
```

Create the role and database, then enable the `citext` extension inside that database. The extension is per database and is required by the `users` table:

```sql
CREATE USER greenlight_user WITH PASSWORD 'your-password';
CREATE DATABASE greenlight OWNER greenlight_user;
GRANT ALL PRIVILEGES ON DATABASE greenlight TO greenlight_user;
\c greenlight
CREATE EXTENSION IF NOT EXISTS citext;
```

### Migrations

The `migrations/` directory holds sequentially numbered `up`/`down` SQL pairs, following the usual migration file convention. There is deliberately no migration tool wired into the project. The files are the source of truth for the schema and are applied manually through `psql`:

```shell
docker exec -i <postgres-container> psql -U greenlight_user -d greenlight \
  < migrations/001_create_movies_table.up.sql
```

Apply them in ascending numeric order on a fresh database, and use the matching `.down.sql` file to roll one back. This keeps the schema history reviewable in Git without adding a CLI dependency to the build and deploy path. If the schema grows to the point where tracking applied versions by hand becomes error prone, this is the piece to swap for a proper migration tool.

### Configuration

Configuration is read from command line flags, with database and SMTP settings defaulting to environment variables. Keeping the SMTP credentials out of the flag defaults means they are never visible in a process listing when the service is started by an init system. Rather than exporting a single pre-built DSN into the shell environment, credentials are kept as discrete variables in a `.env` file, loaded at startup with `joho/godotenv`, and the DSN is assembled in code. That keeps the individual values available to the application, avoids hand encoding reserved characters into a connection string, and means a developer only has to copy a file rather than remember to source one. If `.env` is absent the application falls back to the process environment and logs a warning, so the same binary works unchanged in a deployed environment where the variables are injected by the platform.

Copy `.env.example` to `.env` and fill in the values:

```shell
cp .env.example .env
```

The application exits at startup if `DB_USER`, `DB_PASSWORD` or `DB_HOST` is unset, so a misconfigured environment fails immediately instead of at the first query.

Available flags:

| Flag | Default | Description |
|---|---|---|
| `-port` | `4000` | HTTP server port |
| `-env` | `development` | `development`, `staging` or `production` |
| `-db-user` | `$DB_USER` | Database user |
| `-db-password` | `$DB_PASSWORD` | Database password |
| `-db-name` | `$DB_NAME` | Database name |
| `-db-host` | `$DB_HOST` | Database host |
| `-db-port` | `$DB_PORT` | Database port |
| `-db-sslmode` | `$DB_SSLMODE` | `enable` or `disable` |
| `-db-max-open-conns` | `25` | Max open connections |
| `-db-max-idle-conns` | `20` | Max idle connections |
| `-db-max-idle-time` | `15m` | Max connection idle time |
| `-limiter-rps` | `2` | Rate limiter requests per second |
| `-limiter-burst` | `4` | Rate limiter burst |
| `-limiter-enabled` | `true` | Enable the rate limiter |
| `-smtp-host` | `$SMTP_HOST` | SMTP host |
| `-smtp-port` | `$SMTP_PORT` | SMTP port |
| `-smtp-username` | `$SMTP_USERNAME` | SMTP username. When empty, TLS is disabled for local development |
| `-smtp-password` | `$SMTP_PASSWORD` | SMTP password |
| `-smtp-sender` | `Greenlight API <no-reply@...>` | Sender address |
| `-cors-trusted-origins` | empty | Space separated list of trusted origins |
| `-version` | | Print the build version and exit |

The DSN is assembled with `net/url`, so passwords containing reserved characters such as `@` are escaped correctly and do not need manual encoding.

### Running

```shell
make run/api
```

Or directly:

```shell
go run ./cmd/api -port=4000 -env=development
```

## Make targets

| Target | Description |
|---|---|
| `make help` | List available targets |
| `make run/api` | Run the API |
| `make tidy` | Tidy module dependencies and format all Go files |
| `make audit` | Verify dependencies, vet, run staticcheck and run tests with the race detector |
| `make build/api` | Build binaries into `./bin` |

`make build/api` produces both a native binary and a `linux/amd64` binary, stripped with `-ldflags='-s'`. The version reported by `-version` and by `/v1/healthcheck` is not hardcoded; it is read from the embedded build information via `runtime/debug`, so it reflects the Git tag or revision the binary was built from.
